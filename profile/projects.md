- **Pipelines:** **Ingestion (5 steps)** — insert document row → `DocumentCleaner.cleanText()` (normalise line endings, collapse whitespace) → `TextChunker.chunk()` via LangChain `RecursiveCharacterTextSplitter` (500-char chunks, 80-char overlap, split priority `\n\n` → `\n` → space → char) → `EmbeddingsService.embedBatch()` (all chunks in one batched OpenAI call) → bulk insert into `document_chunks`. **RAG query (9 steps)** — `QueryRewriterService` → `EmbeddingsService.embed()` → `VectorRetrieverService` (Supabase RPC `match_documents()`, cosine `<=>` ordering, optional `source_type` filter) → `RetrievalValidatorService` → `ContextBuilderService` → `PromptBuilderService` → `LlmService.chat()` (GPT-4o-mini, temp 0.3) → `CitationService.formatCitations()` (dedupe by document name) → response `{ answer, sources, tokens_used, retrieval_confidence, metrics, latency_ms }`.
- **Database schema (Supabase/PostgreSQL, 5 migrations):** `documents` (UUID pk, content, `source_type` CHECK in pdf/markdown/slack/github, JSONB metadata), `document_chunks` (`embedding vector(1536)`, chunk_index, JSONB metadata, cascade delete on document), HNSW index `USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`, `match_documents(query_embedding, match_count, filter)` PL/pgSQL similarity-search function returning `1 - (embedding <=> query)` as similarity, plus `chat_sessions` and `messages` (role CHECK, sources JSONB, tokens_used).
- **API:** `POST /ingestion/upload` (+ `/ingestion/process`), `POST /chat`, `GET /chat/sessions`, `GET|POST /documents`, `GET /documents/:id`, `DELETE /documents/:id` (204), and a Next.js `POST /api/upload-pdf` multipart proxy route.
- **Architecture:** monorepo with a NestJS backend and a Next.js frontend; **layered infrastructure** — `LlmService` and `EmbeddingsService` sit behind provider interfaces, so swapping OpenAI for another provider is a new `implements ILLMProvider` class with zero changes to pipeline or business modules; modules split into `infrastructure/` (embeddings, llm + TokenEstimator, supabase, langchain prompts & splitters) and `modules/` (ingestion pipeline, rag pipeline + strategies, chat, documents); the Next.js API routes act as a thin proxy that keeps the backend URL server-side and sidesteps CORS; frontend built from custom hooks (`useChat` with optimistic UI, streaming simulation and session persistence; `useDocuments`; `useSessions`) with shared TypeScript types mirroring backend DTOs. **Testing:** Jest unit tests cover `CitationService`, `ContextBuilderService`, `RetrievalValidatorService`, `VectorRetrieverService` and `TokenEstimatorService`, plus coverage and E2E scripts. ## 11. Job Application Agent (Multi-Agent CV Automation on Claude Code + LinkedIn Assistant)

- **GitHub:** https://github.com/ersinisgor/job-application-agent
- **Local:** /Users/mac/code/ersinisgor/job-application-agent
- **Summary:** **AI agent system** that runs the author's own job search end-to-end, built on **Claude Code** as the agent runtime. A headless **orchestrator agent** picks up every job the user marks for CV generation in a job-application spreadsheet and delegates each one to specialised **subagents** — a CV writer, an optional CV reviewer and a cover-letter writer — that act on the outside world only through a custom **Model Context Protocol (MCP) server** of deterministic Python tools, producing an ATS-optimized, per-posting English CV (Markdown → `.docx` → Google Doc → PDF). A **Chrome MV3 extension** backed by a **FastAPI** service reads the LinkedIn posting on screen and shows a terse Turkish summary (Claude Haiku through the Anthropic API), a deterministic technology-fit score and one-click actions (add the job to the sheet, generate a cover letter through the agent). Design principle: **invariants live in tools, reasoning lives in agents** — the LLM orchestrates and writes, while numbering, de-duplication, locking and output parsing stay in Python code the agents cannot alter. **Migrated from a single-prompt Anthropic API pipeline to this multi-agent architecture** without changing the output format of the 175+ CVs already produced.
- **Tech (AI / agents):** **Claude Code** in headless mode (`claude -p` launched from Python via `subprocess`, `--output-format json`, `--permission-mode dontAsk`, `--strict-mcp-config`, `--disallowedTools`, per-run `--model` / `--effort`); **Claude Code subagents** (`.claude/agents/` — `cv-writer`, `cv-reviewer`, `cover-letter-writer`, each with its own tool allowlist and preloaded skill); **Agent Skills** (`.claude/skills/` — the CV rule set as a `SKILL.md` index plus five rule files, and a cover-letter rule set, not user-invocable); **slash-command orchestrators** (`.claude/commands/` — `/cv-uret`, `/cv-yenile`, `/mektup` with `$ARGUMENTS`); **Claude Code hooks** (`PreToolUse` secret guard, `PostToolUse` output validator) and permission allow/deny rules in `.claude/settings.json`; **Model Context Protocol (MCP)** — custom **stdio MCP server** (`cv-tools`) built with the official Python `mcp` SDK 2.x (`MCPServer`, 7 typed tools) and registered in `.mcp.json`; **Anthropic Claude API** (`anthropic` SDK — Claude Haiku for the panel summary, `temperature=0`, **prompt caching** via `cache_control` on the system prompt, JSON output validated against a Pydantic schema with one retry on malformed JSON); Claude Sonnet for the CV and cover-letter agents; prompt engineering; context engineering.
- **Tech (backend / automation):** **Python 3.14**, **FastAPI** + **Uvicorn** (REST service for the extension), **Pydantic** (typed response schema with `field_validator` normalisation), **Playwright** (headless Chromium scraping of public, guest-view job pages), **BeautifulSoup4** (HTML parsing), **openpyxl** (reads/writes the `.xlsx` workbook, recreating its data-validation dropdowns and copying the table's row formatting on every write), **python-docx** (fills a corporate `.docx` CV template), **Google Drive & Docs API** (`google-api-python-client`, `google-auth`, `google-auth-oauthlib` — service-account access for the workbook, OAuth for personal-Drive document export, `.docx` → Google Doc → PDF), `python-dotenv`, `fcntl` advisory file locking, `threading`, `subprocess`, `argparse` CLIs, rotating logs. **(frontend / extension):** JavaScript, **Chrome Extension Manifest V3** (content script, background service worker, `chrome.storage.local`), custom CSS side panel with light/dark theming, **Shadow DOM and same-origin iframe traversal** to extract content from a hashed-class SPA. **(tools):** Git/GitHub, shell scripts, a macOS `.command` one-click launcher, macOS notifications (`osascript`).
- **Agent workflow:** `/cv-uret` (orchestrator) → `cv_candidates` → for each row, **sequentially**: `prepare_job` (scrape the posting, reserve the CV number, save the job description to a file) → **`cv-writer` subagent** (writes a Turkish ATS analysis plus the English CV into one analysis file) → optional **`cv-reviewer` subagent** behind a feature flag (a second-expert QA pass that audits the draft against the posting and writes a corrected CV) → `finalize_cv` (parse → `.docx` → Google Doc → PDF → spreadsheet). `/cv-yenile <from> <to> [instruction]` regenerates a range of CVs from saved job descriptions and injects a free-text steering instruction as the highest-priority block (it can override layout defaults, never the honesty contract). `/mektup <cv_no> [en|tr] [--force]` → `cover_letter_context` → **`cover-letter-writer` subagent**, which saves its own letter through the `save_cover_letter` tool. MCP tool surface: `cv_candidates`, `prepare_job`, `finalize_cv`, `regen_targets`, `finalize_regen`, `cover_letter_context`, `save_cover_letter`. **File-based hand-off** between agents keeps long artefacts out of the orchestrator's context window, and the analysis file keeps the old API pipeline's response format so the existing parsers were reused unchanged (verified with **0 differences over 175 historical analyses**).
- **Guardrails & safety:** **least-privilege tool scoping** — the orchestrator only has the MCP tools and the Agent tool, the CV subagents only `Read`/`Write`, the letter writer `Read` plus a single MCP tool; the headless session runs in `dontAsk` mode against an allowlist (writes only under `outputs/**`) with deny rules for secrets, and `Bash`, `WebFetch` and `WebSearch` are disabled so agents reach the spreadsheet, LinkedIn and Google Drive only through MCP; `--strict-mcp-config` keeps the user's other connectors out of the agent session; a **`PreToolUse` hook** blocks any tool call that targets credentials, environment files or the user's LinkedIn session cookie; posting text is treated as **untrusted data** whose embedded instructions are never followed (**prompt-injection defence**); a strict **prompt-engineered honesty contract** shipped as an Agent Skill — named technologies may appear only if they exist in the candidate's own profile, and bold text marks every line that differs from the base CV so the output is reviewable as a diff. **Invariants enforced in tools, not prompts:** the CV number is reserved server-side and kept in the MCP server's memory (never read back from the agent), it is consumed only after a successful spreadsheet write, stale output files are deleted on reservation and rejected unless written after the run started, and expired postings are closed with a marker without any model call.
- **Output validation & evaluation:** a **`PostToolUse` hook** runs the same parser that builds the `.docx` on every CV file a subagent writes and returns exit code 2 with the list of problems, so the agent **self-corrects** and rewrites the file before it ever reaches the PDF (checks output markers, section headings, experience entries and bullets, project count against the template's slots, each project's `Tech:` line); the hook was back-tested on **192 historical files with no structural false alarms**. Each headless run's cost, turn count and duration are read from the JSON result and logged, which was used to measure the agent runtime against the previous direct-API pipeline.
- **Key features:** per-posting ATS-tailored CV generation with a Turkish ATS analysis and match rate; on-demand cover letters in English or Turkish, generated from the tailored CV plus the saved job description, cached per (job, language) with a filled sign-off template checked by the save tool; a LinkedIn side panel showing a Turkish summary, work mode, visa/sponsorship, required stack and minimum experience; **deterministic fit scoring computed in Python rather than by the model** — the required stack is modelled as groups of interchangeable alternatives, each option matched against the candidate profile through a synonym/spelling-variant table, and the missing-skill explanation is generated from that diff (the model handled the extraction well but the comparison badly); "reviewed"/"maybe" job markers persisted in extension storage; a one-click **Add** button that appends the posting to the spreadsheet; CV generation triggered when the user marks a row for generation (apply time, not bookmark time), by a background poller or a one-click launcher; `--dry-run` / `--limit` / `--row` one-shot CLI and a regeneration CLI with a free-text steering instruction.
- **Engineering details worth calling out:** **cross-process concurrency** — the MCP server, the poller and the API all mutate the same workbook, so every mutating method runs inside an advisory `flock` (download → edit → upload as one critical section) with a timeout, while pure reads stay lock-free on purpose; an in-process `threading.Lock` guards the append endpoint because FastAPI runs sync endpoints in a threadpool and a double-click could otherwise put two requests past the duplicate check; a separate non-blocking lock guarantees the poller and the manual launcher never run two CV batches at once. **Cost control** — the poller checks the spreadsheet in plain Python and launches an agent only when there is work, so idle rounds cost nothing; a 15-minute retry cooldown per job; model routing (fast Haiku call for the per-click summary, Sonnet agents for CVs) with per-run effort levels; the API key is stripped from the agent's environment so agent runs use the Claude subscription instead of API billing. **Caching** — an LRU result cache keyed by job id, mirrored to disk and stamped with a version number that invalidates every entry whenever the scoring rubric or the candidate profile changes; a 5-minute spreadsheet snapshot so a panel click costs at most one download, with a forced refresh on a miss. **Resilience** — atomic `tmp` + `replace` file writes, per-run timeouts on agent sessions, a staged-description fallback path that is deliberately logged and alerted rather than applied silently, structured logging to a rotating log plus a failure log and desktop notifications, and a timeout-and-explain path in the extension instead of an infinite spinner.
- **Architecture:** `config.py` centralises settings and paths; `main.py` runs the poll loop → `agent_runner.py` (headless Claude Code launcher with locking, timeouts and a sanitised environment) → Claude Code session (orchestrator command + subagents + skills + hooks) → `mcp_server.py` (cv-tools) → `pipeline.py` / `scraper.py` / `cv_output.py` / `docx_builder.py` / `drive_docs.py` / `cover_letter.py`, with all spreadsheet I/O funnelled through `sheets.py` and observability through `reporting.py`. The extension talks to `summary_api.py` (FastAPI) through a background service worker; the API is the only place that calls the Anthropic API directly. A hard **import-isolation rule** keeps the API process free of the scraping stack: `joblookup.py` exists solely to hold the lookups the API needs so it never imports the Playwright-dependent pipeline or the MCP server, and the rule is enforced by a scripted check. Agent definitions, skills, prompts and profile data live as editable Markdown assets (`.claude/`, `prompts/`, `profile/`), so changing what the CV may claim or how an agent behaves is a data edit, not a code change.
